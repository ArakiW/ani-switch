## 预研结论 (2026-09-10 调研,先于实机 log)

读了 mbedTLS 2.28.10 `library/ssl_ciphersuites.c` `ciphersuite_preference[]` +
`ssl_tls.c` `ssl_preset_default_hashes[]` 源码。

**Cipher list** 第一项是 `ECDHE-RSA-WITH-CHACHA20-POLY1305-SHA256` (0xCCA8),
第二项 `ECDHE-ECDSA-WITH-CHACHA20-POLY1305-SHA256` (0xCCA9), 第三项
`DHE-RSA-WITH-CHACHA20-POLY1305-SHA256` (0xCCAA), 第四项起才是
`ECDHE-ECDSA-AES-256-GCM-SHA384` (0xC02C)。Cloudflare 1.3 edge 也接受 CHACHA20
(ARM64 NEON 加速),但**某些 POP 优先选 AES-GCM** — 如果 server 选 client
list 第一个它支持的,可能跳过 CHACHA20 选 0xC030, 不会 reject。

**`sig_hashes` 默认**:
```c
ssl_preset_default_hashes[] = {
    MBEDTLS_MD_SHA512, MBEDTLS_MD_SHA384,    // (若 MBEDTLS_SHA512_C)
    MBEDTLS_MD_SHA256, MBEDTLS_MD_SHA224,    // (若 MBEDTLS_SHA256_C)
    // 后面: SHA1 only if MBEDTLS_TLS_DEFAULT_ALLOW_SHA1_IN_KEY_EXCHANGE
    MBEDTLS_MD_NONE
};
```

devkitpro 20260219 portlibs mbedTLS 2.28.10 build **没** define
`MBEDTLS_TLS_DEFAULT_ALLOW_SHA1_IN_KEY_EXCHANGE`(只注释提到,无 `#define`),
所以 **SHA1 默认不发** — RFC 9155 要求满足,case C 不可能。

**结论**:
- case B (cipher mismatch) — 不太可能,Cloudflare 接受 CHACHA20
- case C (signature_algorithms 含 SHA1) — 不可能,devkitpro 编译时已排除
- case A (IP resolve) — **最可能**。hardcoded IP `104.26.8.23` 是 2026-09-08
  解析的,Cloudflare anycast 边缘每天 rotate,可能已 stale
- case D (cert chain) — 较不可能,`verify_peer=false` 已关

## 拿到 startup.log 后,按这个 4-case 决策树走

### Case A — 实际是 IP resolve 失败,不是 mid-TLS

**v19.0.2 已预防性 ship,基本不会触发了。**

`startup.log` 看到 `Connection reset by peer` **在 ClientHello 之前**:
```
HTTP: RESOLVE api.bgm.tv -> 104.26.8.23 (hardcoded)
[+] Connecting to 104.26.8.23:443
[Recv failure: Connection reset by peer]   ← 在 [SSL_DATA_OUT] 之前
```

**根因**:hardcoded IP 失效。Cloudflare anycast edge IP 每天 rotate,
`kHardcodedHosts[]` table 6 个 IP (`api.bgm.tv -> 104.26.8.23` 等) 都
是 2026-09-08 解析的,到今天 90% 概率 stale。

**修法**:应用 `docs/v19.0.2-case-A.patch` —
1. 删 `kHardcodedHosts[]` + `lookupHardcodedHost()` (src/net/http.cpp:21-48)
2. `rewriteUrlForIP()` 删 hardcoded 优先分支,直接走 cache → raw UDP DNS
3. 实际效果:ani-switch 启动第一次访问每个 host 走 raw UDP DNS (8.8.8.8,
5s timeout),成功后 30 min in-memory cache 复用

**估计 1-2 hour ship + 1 次 docker build**。

### Case B — cipher mismatch (低概率,1-5%)

`startup.log` 看到 ClientHello 发出 (`[out] 16 03 01 02 00 01 ...`) 但
ServerHello 没回,server RST:
```
[SSL_DATA_OUT] 16 03 01 02 00 01 00 01 fc 03 03 ... 0c 02 c0 30 ...
Recv failure: Connection reset by peer
```

**修法 (B')**:完全 bypass cpr/curl 整套栈,自己用 mbedTLS 2.28 API 重建
HTTP/1.1 client。1-2 天 ship,见下文 B'+C' 方案。

### Case C — 不可能 (devkitpro 编译 flag 排除 SHA1)
跳过。

### Case D — cert verify fail (低概率,5-10%)

`startup.log` 看到 `[cert verify result: BADCERT_NOT_TRUSTED]` 或
`MBEDTLS_ERR_SSL_BAD_CERTIFICATE` 错:
```
mbedTLS: ssl_parse_record returned -0x7C00
[cert verify result: BADCERT_NOT_TRUSTED]
```

**根因**:ca-bundle.crt 缺 Cloudflare ISRG Root X1 (Let's Encrypt) 中间 cert。
但 mbedTLS 2.28 default `verify_mode = NONE` 走不到 cert verify — 如果
走到了,说明 `verify_peer=true` 不小心开了。

**修法**:verify case A 同样删 hardcoded IP,如果还 fail,改 mbedtls x509
trust store 加载 ca-bundle.crt + 设 `verify_peer=true`。

## 备份方案

### B' + C' (一次解决 B 和 C,如果 case A 修完还不够)

完全重建 HTTP 栈,绕开 cpr/curl 8.4 + mbedTLS 2.28 backend:

```cpp
// runtime/tls/mbedtls_direct.hpp
class DirectTLS {
    mbedtls_ssl_context ssl;
    mbedtls_ssl_config  conf;
    mbedtls_x509_crt    cacert;        // Mozilla ca-bundle.crt
    int                 fd;
    // ...
public:
    void configure(CipherList, SigHashes, Hostname, CAPath);
    Response execute(Request);
};
```

直接调 mbedTLS 2.28 API,精细控制:
- `mbedtls_ssl_conf_ciphersuites()` 显式 list (4 个 cipher, AES-256-GCM 优先)
- `mbedtls_ssl_conf_sig_hashes()` 显式 algo (SHA256 / SHA384 / SHA512)
- `mbedtls_ssl_set_hostname()` SNI = hostname
- `mbedtls_x509_crt_parse_file()` 加载 ca-bundle.crt
- libnx BSD socket 直连

**预计 1-2 天 ship**。HTTP/1.1 keepalive + chunked + gzip 都手写,
只覆盖 ani-switch 用到的 GET/POST 路径 ~500 行代码。
